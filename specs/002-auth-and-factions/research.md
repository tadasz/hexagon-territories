## R1. Verifying Apple identity tokens with `jose`

- **Decision**: `apps/api/src/modules/auth/apple.ts` exposes `interface AppleTokenVerifier { verify(identityToken: string): Promise<AppleIdentity> }` with `AppleIdentity = {sub, email?, emailVerified?, isPrivateEmail?}`. The production implementation `JoseAppleVerifier` uses `jose.createRemoteJWKSet(new URL(config.apple.jwksUrl), { cooldownDuration: 30_000, cacheMaxAge: 600_000 })` and `jose.jwtVerify(token, jwks, { issuer: 'https://appleid.apple.com', audience: config.apple.clientIds, algorithms: ['RS256'] })`. Failures map to: signature/claims errors → `401 INVALID_APPLE_TOKEN` (details: `reason` = `expired | audience | issuer | signature | malformed`); JWKS fetch errors (`JWKSNoMatchingKey` after a refresh, network, timeout) → `503 APPLE_UNAVAILABLE`. `config.apple.clientIds` is `APPLE_CLIENT_IDS` split on commas (default `com.natureexplorer.app`, the placeholder bundle id). `APPLE_JWKS_URL` defaults to `https://appleid.apple.com/auth/keys` and is overridable so tests and the dev stub can serve their own keys.
- **Tests**: `test/helpers/apple.ts` generates an RS256 key pair (`jose.generateKeyPair`), serves `{keys: [jwk]}` from an in-process `node:http` server on an ephemeral port, and exports `mintIdentityToken({sub, email?, aud?, exp?, kid?})`. Unit tests cover valid, wrong audience, wrong issuer, expired, unknown `kid`, malformed string, and JWKS server down (→ `APPLE_UNAVAILABLE`). No test contacts Apple.
- **Dev stub**: `apps/api/scripts/apple-stub.ts` (`pnpm --filter @nature/api dev:apple-stub`) runs the same helper on port 4567 and prints a minted token for `--sub` and `--email`, so `quickstart.md` can drive the whole flow with `curl` (`APPLE_JWKS_URL=http://localhost:4567/keys`).
- **Rationale**: `jose` is the constitution-friendly boring choice (no native deps, ESM, maintained), already the decided library; caching JWKS in process avoids a fetch per sign-in and survives brief Apple outages; injecting the verifier keeps unit tests offline (Constitution V).
- **Alternatives considered**: `apple-signin-auth` (wraps the same steps, extra dependency); `@fastify/jwt` for Apple (built for our own tokens, awkward for remote JWKS); verifying only on the client (violates Constitution I's spirit and Apple guidance).

## R2. Access and refresh tokens

- **Decision**: `modules/auth/tokens.ts`. **Access**: `jose.SignJWT` HS256 with `JWT_SECRET` (min 32 chars, validated by config), claims `{sub: userId, role, iss: 'nature-api', aud: 'nature-ios', iat, exp: iat + JWT_ACCESS_TTL_S (900)}`; verified with `jose.jwtVerify` (same issuer/audience) → `401 TOKEN_EXPIRED` or `401 UNAUTHORIZED`. **Refresh**: 32 random bytes → base64url string handed to the client; stored as `sha256(token)` in `refresh_tokens.token_hash` (`bytea`, unique) with `expires_at = now + REFRESH_TTL_DAYS (60)`. **Rotation**: `refresh(token)` in one transaction: look up by hash; if missing or `expires_at < now` → `401 INVALID_REFRESH_TOKEN`; if `revoked_at` is set → **reuse**: `UPDATE refresh_tokens SET revoked_at = now() WHERE user_id = ? AND revoked_at IS NULL`, then `401 REFRESH_REUSED`; else set `revoked_at = now()` on the row, insert the successor, mint a new access token, update `users.last_seen_at`. Concurrency: the lookup uses `SELECT … FOR UPDATE`, so two racing refreshes serialise and the second sees `revoked_at` set (reuse path), which is the accepted behaviour (spec edge case). **Cleanup**: on every successful refresh, `DELETE FROM refresh_tokens WHERE user_id = ? AND (expires_at < now() - interval '7 days' OR revoked_at < now() - interval '7 days')` keeps the table bounded without a job. **Logout**: `POST /v1/auth/logout {refreshToken}` sets `revoked_at` if the token belongs to the caller; always `204`.
- **Rationale**: matches the feature decision (HS256 15 min, 60-day rotating hashed refresh, revocation on reuse); hashing means a database leak reveals no usable credential; `FOR UPDATE` gives correctness without a token-family column (the 001 table has none, and revoking the whole user on reuse is the decided policy).
- **Alternatives considered**: `@fastify/jwt` + `@fastify/auth` (extra plugins for two functions `jose` already provides); RS256 access tokens (no second verifier exists yet; HS256 is decided); token families with `family_id` (needs a migration for a distinction the policy does not use).

## R3. Auth plugin and `request.user`

- **Decision**: `plugins/auth.ts` (fastify-plugin, depends on `db`): decorates `fastify.authenticate` (a `preHandler`) and `request.user: AuthUser | null` (`{id, role, factionId, lastSeenAt}`). `authenticate` reads `Authorization: Bearer …`, verifies the access JWT (R2), loads `users` by primary key (`id, role, faction_id, deleted_at, last_seen_at`), answers `401 UNAUTHORIZED` (missing/invalid), `401 TOKEN_EXPIRED`, `401 ACCOUNT_DELETED` (`deleted_at` set), and updates `last_seen_at` when null or older than 15 minutes (fire-and-forget `UPDATE`, errors logged, never failing the request). Routes opt in with `{ preHandler: [fastify.authenticate] }` and declare `security: [{ bearerAuth: [] }]` in their schema so the OpenAPI document (and the generated Swift client) carries the requirement. `fastify.requireFaction` is **not** added here (003 adds it when walks need a faction).
- **Rationale**: one PK lookup per authenticated request is cheap at beta scale and gives instant enforcement of deletion and role changes (the JWT alone would honour a deleted account for up to 15 minutes); the throttle keeps `last_seen_at` writes to ≤ 4 per player per hour.
- **Alternatives considered**: trusting JWT claims without a lookup (delays deletion enforcement); an `onRequest` hook applied globally with an allow-list (implicit; the explicit preHandler is easier to review per route).

## R4. Rate limiting `/v1/auth/*`

- **Decision**: `@fastify/rate-limit` registered once in `plugins/rate-limit.ts` with `global: false`; the auth routes set `config: { rateLimit: { max: config.authRateLimitPerMin (20), timeWindow: '1 minute' } }`. Key: client IP (`request.ip`; `trustProxy` is enabled in `buildApp` only when `TRUST_PROXY=true`, which the Caddy deployment of 009 will set). The plugin's `errorResponseBuilder` returns an `AppError(429, 'RATE_LIMITED', …, { retryAfterS })` so the 001 error handler serialises the shared envelope, and the `retry-after` header is kept. Store: in-memory (single instance; documented in `plan.md` Deviations).
- **Rationale**: decided library; route-level config keeps every other endpoint unthrottled (spec); the envelope stays consistent (FR-005).
- **Alternatives considered**: a Postgres-backed store via the plugin's `store` option (possible later, not needed for the beta); global limiting (would throttle map reads in 005).

## R5. Faction statistics and the suggestion query

- **Decision**: `modules/factions/service.ts` runs one query per request:

  ```sql
  SELECT f.id, f.slug, f.name, f.emoji, f.color_light, f.color_dark, f.sort,
         COUNT(u.id) FILTER (WHERE u.deleted_at IS NULL)                                   AS members,
         COUNT(u.id) FILTER (WHERE u.deleted_at IS NULL AND u.last_seen_at >= $1)          AS active_members,
         (SELECT COUNT(*) FROM hex_state h WHERE h.owner_faction_id = f.id)                 AS hexes_owned_r9,
         (SELECT COUNT(*) FROM hex_parent_state p WHERE p.res = 7 AND p.owner_faction_id = f.id) AS hexes_owned_r7
  FROM factions f LEFT JOIN users u ON u.faction_id = f.id
  GROUP BY f.id ORDER BY f.sort, f.id
  ```

  with `$1 = now() - ACTIVE_PLAYER_WINDOW_DAYS`. `suggestedFactionId` = the first row after sorting by `(active_members ASC, id ASC)`. Migration `0003` adds `users_faction_active_idx ON users (faction_id, last_seen_at) WHERE deleted_at IS NULL` so both counts are index-only; `hex_state(owner_faction_id)` and `hex_parent_state(owner_faction_id)` indexes exist from 001. `GET /v1/factions` needs no session and sets `Cache-Control: public, max-age=60`. `GET /v1/me` reuses the same service function to fill `suggestedFactionId` (cost is negligible; simpler than caching).
- **Rationale**: FR-006 and Shared Semantics 5; counts are derived, never stored, so they are always live and zero-safe in an empty world; the ordering rule makes ties deterministic.
- **Alternatives considered**: reading `faction_stats_weekly` (written only by the reckoning from 004, stale between runs); a materialised view (unneeded at this scale).

## R6. Faction change lock and the account constants

## R7. Account deletion: soft delete, purge job, purge registry

- **Decision**: `DELETE /v1/me` (authenticated) in one transaction: `users.deleted_at = now()`, revoke all refresh tokens, then `boss.send('account.purge', {userId, deletedAt}, { startAfter: deletedAt + ACCOUNT_PURGE_GRACE_DAYS, singletonKey: userId, retryLimit: 5, retryBackoff: true })`; responds `200 {deletedAt, purgeAt}`. `jobs/account-purge.ts` re-reads the user and **exits without changes** unless `deleted_at IS NOT NULL AND deleted_at <= now() - 30 days` (handles restore-on-sign-in and reruns). Erasure runs `purgeUser(db, storage, userId)` from `modules/me/purge.ts`, a registry of ordered steps `PurgeStep {name, tables: string[], run(tx, userId)}`; 002 registers: `exports` (delete `account_exports` rows and their objects from storage), `refresh_tokens`, `devices`, and finally `users` (the `users` step deletes the row; cascades cover `user_species`, `streaks`). `test/unit/purge-registry.test.ts` (and the integration `delete-purge.test.ts`) query `information_schema` for every foreign key that references `users` and fail unless the referencing table is either `ON DELETE CASCADE`, `ON DELETE SET NULL`, or named in a registered step's `tables` — so features 003+ (`walk_sessions`, `captures`, `hex_week_contribution`, `points_ledger`, `leaderboard_snapshots`, `anti_cheat_flags`) must register a step (delete or anonymise) before they can merge. Restore: `POST /v1/auth/apple` for a `sub` whose user has `deleted_at` set clears it (and the job's own guard skips the purge; no job cancellation is attempted).
- **Rationale**: FR-010/FR-011, Constitution IV, App Store 5.1.1(v). pg-boss `startAfter` + `singletonKey` gives one delayed job per account with retries; the guard makes the job idempotent and restore-safe; the FK-coverage test turns "deletion must keep working in every release" into CI.
- **Alternatives considered**: a daily sweeper job scanning `deleted_at` (simpler scheduling, but a second code path and no per-account retry story); hard delete immediately (no grace period, contrary to §5); storing the job id for cancellation (unnecessary given the guard).

## R8. Data export: table, self-enqueuing GET, sections, storage

- **Decision**: table `account_exports (id uuid pk, user_id fk cascade, status 'pending'|'ready'|'failed', object_key text, requested_at, completed_at, expires_at, error text)` (`data-model.md` §1.1). `GET /v1/me/export`: select the latest export for the user; if it is `pending`, or `ready` with `expires_at > now()`, return it (`200`; for `ready` add a fresh presigned GET URL valid 1 h); otherwise insert a new `pending` row, `boss.send('account.export', {exportId, userId}, { singletonKey: exportId, retryLimit: 3 })`, return `202 {status: 'pending', requestedAt}`. `jobs/account-export.ts` builds the bundle by calling every registered `ExportSection {name, run(db, userId) → JsonValue}` from `modules/me/export-sections.ts` (002 registers `account`, `factions`, `sessions` — see `data-model.md` §4), writes `exports/<userId>/<exportId>.json` (`application/json`) via `fastify.storage`, sets `ready`, `completed_at`, `expires_at = completed_at + EXPORT_TTL_DAYS (7)`; on error sets `failed` with a short `error` (no PII). Objects are also expired by the bucket lifecycle rule (`minio-init`: `mc ilm rule add --expire-days 7 --prefix exports/`), and the purge step deletes them explicitly.
- **Rationale**: FR-012 and Shared Semantics 10; the registry lets 003+ add `walks`, `captures`, `collection` sections without touching this job; a single GET keeps the client simple (one call, poll) while staying idempotent for pending/fresh exports (documented deviation).
- **Alternatives considered**: `POST` to request + `GET` to poll (cleaner HTTP, but §5 names one `GET`, and the decision binds); synchronous export in the request (fine for 002's tiny bundle, wrong once walks and media exist); streaming through the API (violates "media never passes through the API").

## R9. Object storage abstraction (`lib/storage.ts`)

- **Decision**: `interface ObjectStorage { putObject(key, body: Buffer | string, contentType): Promise<void>; getObject(key): Promise<Buffer | null>; deleteObject(key): Promise<void>; presignGet(key, expiresInS): Promise<string>; presignPut(key, contentType, expiresInS, maxBytes?): Promise<string> }`. `S3ObjectStorage` wraps `@aws-sdk/client-s3` (`S3Client` with `endpoint: S3_ENDPOINT`, `region: S3_REGION` (default `eu-central-1`), `forcePathStyle: true`, credentials from `S3_ACCESS_KEY/S3_SECRET_KEY`) and `@aws-sdk/s3-request-presigner`; when `S3_PUBLIC_ENDPOINT` is set, presigned URLs are generated against a second client whose endpoint is the public one (so a phone on the LAN or the internet can reach MinIO/Hetzner while the API talks to the internal address). `MemoryObjectStorage` (map-backed, presigned URLs are `memory://<key>?exp=`) is used in unit tests and by the export job tests. `plugins/storage.ts` decorates `fastify.storage`; `buildApp` accepts `storage?: ObjectStorage` for tests. `presignPut` is unused in 002 but defined now so 006/007 media uploads use the same interface (feature decision).
- **Tests**: unit tests over `MemoryObjectStorage` and over `S3ObjectStorage` with the SDK's request layer stubbed (assert bucket/key/content-type and that the presigned URL host follows `S3_PUBLIC_ENDPOINT`); an integration test against MinIO runs only with `S3_TEST=1` (`quickstart.md` documents it for Docker machines).
- **Rationale**: ADR 0010 and the feature decision; the AWS SDK v3 is the reference client for S3-compatible stores and supports path-style MinIO; the memory fake keeps tests hermetic.
- **Alternatives considered**: `minio` npm client (works with Hetzner too, but ties the abstraction to one vendor's SDK); raw SigV4 signing (more code to get wrong).

## R10. OpenAPI snapshot package `@nature/api-schema`

- **Decision**: `apps/api/src/openapi/print.ts` builds the app with `jobs: false`, a no-op `dbPing`, `MemoryObjectStorage` and a placeholder config (no database connection is opened: the `db` plugin's pool is lazy), awaits `app.ready()`, prints `JSON.stringify(app.swagger())` and exits; script `openapi:print`. `packages/api-schema/scripts/snapshot.ts` runs `pnpm --filter @nature/api openapi:print` (`execFileSync`, `cwd` = repo root), formats with `prettier.format(json, { parser: 'json' })` and writes `packages/api-schema/openapi.json`. `test/snapshot.test.ts` regenerates in memory the same way and asserts byte equality with a message `openapi.json is stale — run pnpm --filter @nature/api-schema snapshot`; a second test asserts `apps/ios/Packages/APIClient/Sources/APIClient/openapi.json` equals the snapshot when that file exists (skipped with a note otherwise). `package.json` (`@nature/api-schema`, private, scripts `build` (tsc), `test`, `lint`, `typecheck`, `clean`, `snapshot`; devDependencies `@nature/api: workspace:*` so turbo builds the API's workspace deps first, `prettier`, `vitest`, `tsx`). `src/index.ts` exports only `OPENAPI_PATH` (the absolute path of the snapshot); it deliberately does not re-export the API's error-code list, which would couple the package's build to `apps/api` internals — consumers read the codes from the document's `Error.examples`.
- **Rationale**: the constitution's "contracts merged into `packages/api-schema`; iOS client generated" with the runtime document as the source of truth (feature decision); prettier formatting keeps `pnpm lint` (`prettier --check .`) green without ignoring the file; the staleness test is the merge gate (SC-007).
- **Alternatives considered**: importing `buildApp` directly in the package (needs `exports`/declarations from `@nature/api`, which is an app, not a library); committing YAML (the runtime document is JSON; converting adds a dependency and a second format to diff).

## R11. iOS client generation

- **Decision**: `apps/ios/Packages/APIClient/Package.swift` depends on `swift-openapi-generator` (plugin), `swift-openapi-runtime`, `swift-openapi-urlsession` (all `from: "1.0.0"`) and `Core`; `Sources/APIClient/openapi-generator-config.yaml`: `generate: [types, client]`, `accessModifier: public`, `namingStrategy: idiomatic`; `Sources/APIClient/openapi.json` is a **copy** of the snapshot written by `apps/ios/scripts/sync-openapi.sh` (Stream C runs it; the `@nature/api-schema` test keeps it honest). `AuthMiddleware: ClientMiddleware` asks `AuthSession` for a bearer token, adds the header, and on `401` asks the session to refresh once and retries once (Shared Semantics 2). `APIClientFactory.make(baseURL:session:)` returns the generated `Client` with `URLSessionTransport` and the middleware; `Adapters/{AuthServiceLive,FactionsServiceLive,ProfileServiceLive}.swift` implement the `Core` protocols by calling the generated operations and mapping generated types to `Core` models and `APIError` (from the `Error` envelope's `code`). Generation runs at build time on macOS/Xcode Cloud; nothing generated is committed. Linux: the package is not built (swift-openapi-generator can run on Linux, but the container's SPM network access is not guaranteed — optional attempt recorded in `VERIFY.md`).
- **Rationale**: constitution ("the iOS client is generated, never hand-written"); the middleware is the documented extension point; adapters keep the feature packages and `Core` independent of generated types so `Core` tests run on Linux with fakes.
- **Alternatives considered**: symlinking the snapshot (unverifiable on macOS from here; `plan.md` Deviations); a hand-written `URLSession` client (forbidden); `OpenAPIAsyncHTTPClient` transport (server-side library).

## R12. iOS session architecture (`Core`, `AuthSession`, Keychain, gating)

- **Decision**: `Core` (Foundation + Observation only) holds: models (`Me`, `Faction`, `FactionStats`, `FactionsResponse`, `TokenPair`, `ExportStatus`, `AccountDeletion`), protocols (`AuthService`, `FactionsService`, `ProfileService`, `TokenStore`, `Clock`), `APIError`, and the `AuthSession` actor: `state: AuthState = .signedOut | .signedIn(TokenPair) | .refreshing(Task<TokenPair, Error>)`; `restore()` loads the pair from `TokenStore` at launch; `signIn(identityToken:authorizationCode:fullName:)` calls `AuthService.signInWithApple`, stores the pair; `validAccessToken()` returns the token if `accessExpiresAt - 30 s > clock.now()`, otherwise refreshes; `refresh()` is single-flight (a concurrent caller awaits the in-flight task); a refresh failing with `APIError.unauthorized/refreshReused/accountDeleted` clears the store and sets `.signedOut`; network errors keep the state and rethrow; `signOut()` calls `AuthService.logout` best-effort, clears the store, sets `.signedOut`; `authStateChanges: AsyncStream<AuthState>` feeds the UI. `KeychainStore: TokenStore` (in `AuthFeature`, iOS-only) stores the JSON-encoded pair under one generic-password item with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; `InMemoryTokenStore` (in `Core`, for tests and previews). `RootView` observes `AppContainer.sessionState` (`@Observable` mirror of the actor's stream, `@MainActor`) and `AppContainer.me`: `.signedOut` → `SignInView`; signed in and `me.factionId == nil` → `FactionPickView`; else the six-tab `TabView`. View models (`AuthViewModel`, `FactionsViewModel`, `ProfileViewModel`) are `@Observable @MainActor` classes in the feature packages that call the protocols and reuse `Core` presentation helpers (`FactionPickPresentation`, `FactionChangeLock`, `DisplayNameValidator`, `ExportPresentation`).
- **Rationale**: FR-016/SC-008 (Linux-testable logic), §4 pattern (protocol-typed services from `AppContainer`), refresh-on-401 with single-flight is the standard mobile session design and is where bugs hide, so it is the most-tested unit.
- **Alternatives considered**: keeping `AuthSession` inside `AuthFeature` (would need SwiftUI-free targets anyway); `@Observable` inside the actor (Observation is not actor-friendly; a MainActor mirror is simpler); storing tokens in `UserDefaults` (not acceptable for credentials).

## R13. Sign in with Apple on iOS

- **Decision**: `SignInView` uses `SignInWithAppleButton(.signIn) { request in request.requestedScopes = [.fullName, .email] } onCompletion: { … }`; on success it reads `ASAuthorizationAppleIDCredential.identityToken` (Data → UTF-8 string), `authorizationCode` (Data → string), and `fullName` (`PersonNameComponents`, present only on the first authorization) and calls `AuthViewModel.signIn(...)` → `AuthSession.signIn`. Errors: `ASAuthorizationError.canceled` is silent; anything else shows a retry banner. `project.yml` adds the entitlement file `NatureExplorer/NatureExplorer.entitlements` with `com.apple.developer.applesignin = [Default]` and `CODE_SIGN_ENTITLEMENTS`; the capability must also be enabled on the App ID by the owner (`plan.md` "Owner actions"). Simulator: Sign in with Apple works when the simulator is signed into an Apple ID; otherwise the dev stub (R1) plus `API_BASE_URL` is the documented fallback for API testing.
- **Rationale**: Apple's SwiftUI button is the required UI (Human Interface Guidelines); requesting name/email only matters on first authorization, which matches "store from the first payload"; the entitlement is mandatory for the button to work.
- **Alternatives considered**: `ASAuthorizationController` in UIKit (more code, same result); requesting `.email` only (loses the given-name default display name).

## R14. Logging and privacy

- **Decision**: `buildApp` configures pino `redact: { paths: ['req.headers.authorization', 'req.headers.cookie', '*.email', '*.identityToken', '*.refreshToken', '*.accessToken', 'body.email', 'body.identityToken', 'body.refreshToken'], censor: '[redacted]' }`; the auth module logs `sub` hashes (first 8 hex chars of `sha256(sub)`) rather than raw identifiers, never e-mails; `test/unit/auth-logging.test.ts` captures log output with a pino destination stream during a sign-in and asserts the e-mail and tokens do not appear (FR-015).
- **Rationale**: Constitution IV and the feature decision "log no emails"; redaction at the logger is the one place that catches accidental object logging.
- **Alternatives considered**: relying on discipline in each log call (fails silently).
