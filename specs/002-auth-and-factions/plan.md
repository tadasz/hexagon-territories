## Summary

Add identity and faction membership on top of the 001 skeletons. **API**: Sign in with Apple verified against Apple's JWKS (`jose`), users upserted by Apple `sub`; HS256 access JWT (15 min) plus rotating, hashed refresh tokens (60 days) with reuse revocation; an `auth` plugin decorating `request.user`; per-IP rate limiting on `/v1/auth/*`; `GET /v1/factions` with live stats and the smallest-faction suggestion; `GET/PATCH /v1/me`, `POST /v1/me/faction` (first pick free, then one change per 30 days), `DELETE /v1/me` (soft delete + `account.purge` job after 30 days, with a purge registry and an FK-coverage test), `GET /v1/me/export` (self-enqueuing `account.export` job writing a JSON bundle to object storage through a new `lib/storage.ts` S3 abstraction, presigned GET URL). **Contract**: the API's generated OpenAPI is snapshotted into a new `packages/api-schema` (`@nature/api-schema`) with a staleness test. **iOS**: a Linux-testable `Core` package (models, service protocols, `AuthSession` actor with refresh-on-401, validators and presentation logic), an `APIClient` package generated by `swift-openapi-generator` from the snapshot, and `AuthFeature` / `FactionsFeature` / `ProfileFeature` SwiftUI packages wired into `AppContainer` and a gated `RootView` with six tabs. Work runs as three streams: **A api**, **B ios** (parallel, disjoint paths), **C integration** afterwards. Decisions are in `research.md`, shapes in `data-model.md`, endpoints in `contracts/openapi.yaml`, tasks in `tasks.md`.

## Shared Semantics (server and client must agree)

Defined once here so Stream A (API) and Stream B (iOS) implement the same behaviour without talking to each other. Types: `data-model.md`; endpoints: `contracts/openapi.yaml`.

1. **Sign-in payload**: the app sends Apple's `identityToken` (JWT string), the `authorizationCode` (opaque string, optional, stored nowhere in 002), and `fullName {givenName?, familyName?}` only when Apple supplied it (first authorization). The server ignores `fullName` for existing users.
2. **Token pair**: `{accessToken, accessExpiresAt (ISO 8601), refreshToken, refreshExpiresAt}`. The client treats the access token as expired 30 s before `accessExpiresAt` (clock skew) and refreshes proactively; on any `401` it refreshes once and retries the request once; if the refresh fails with `401` (`INVALID_REFRESH_TOKEN`, `REFRESH_REUSED`, `ACCOUNT_DELETED`) it clears the Keychain and shows the sign-in screen; on network errors it keeps the session and surfaces the error.
3. **Refresh rotation**: `POST /v1/auth/refresh {refreshToken}` returns a new pair and revokes the presented token (`revoked_at = now`). Presenting a token that is revoked, expired or unknown → `401 INVALID_REFRESH_TOKEN`; presenting a token that was *rotated* (revoked but not expired and has a successor) → all refresh tokens of that user are revoked and the answer is `401 REFRESH_REUSED`. The server distinguishes the two only for logging; the client treats both as "sign in again".
4. **Deleted accounts**: `deleted_at` set → every authenticated request answers `401 ACCOUNT_DELETED`; refresh answers the same; sign-in with the same `sub` inside the grace period clears `deleted_at` (restore) and issues tokens normally; the purge job re-checks `deleted_at IS NOT NULL AND deleted_at <= now() - 30 days` before deleting.
5. **Suggestion**: `suggestedFactionId = argmin over factions of activeMembers` where `activeMembers = count(users where faction_id = f and deleted_at is null and last_seen_at >= now() - 14 days)`; ties → lowest `factions.id`; returned by `GET /v1/factions` and `GET /v1/me`. The client pre-selects it on the pick screen and labels it "Fewest active players"; the client never recomputes it.
6. **Faction change**: `POST /v1/me/faction {factionId}`: unknown id → `404 FACTION_NOT_FOUND`; same as current → `200` unchanged; `faction_id` null → set, `faction_changed_at` stays null (first pick free); otherwise if `faction_changed_at` is null or `≤ now() - 30 days` → set faction and `faction_changed_at = now()`; else `409 FACTION_CHANGE_LOCKED` with `details.nextChangeAt`. `Me.factionChangeAvailableAt` = `faction_changed_at + 30 days` or null when a change is allowed now; the client shows the lock from this field only.
7. **Display name**: trim Unicode whitespace; length counted in Unicode scalars must be 2–24; reject any control character (Unicode category Cc) including `\n`, `\r`, `\t`; the same rule is implemented in `apps/api/src/modules/me/display-name.ts` and `Core/Validation/DisplayNameValidator.swift` and both test the same cases (`data-model.md` §2.7).
8. **Default display name**: Apple `givenName` trimmed if it passes rule 7, else `Explorer ` + four random digits (`Explorer 0421` style, zero-padded).
9. **`last_seen_at`**: updated by the auth plugin when null or older than 15 minutes, and always on sign-in and refresh. Never updated by `GET /v1/factions` (no session).
10. **Export states**: `pending → ready | failed`; `ready` carries `downloadUrl` (presigned GET, 1 h) and `expiresAt` (= `completedAt + 7 days`); `GET /v1/me/export` returns the latest export if it is `pending`, or `ready` and not expired, or `failed` less than 1 minute old is *not* reused — a failed or expired export causes a new one to be enqueued and `202 {status: pending}`; a brand-new request also answers `202`. The client polls every 5 s while pending (max 5 min, then shows "still preparing, come back later").
11. **Delete**: `DELETE /v1/me` → `200 {deletedAt, purgeAt}`; the client clears the Keychain immediately regardless of the response body.
12. **Errors**: every non-2xx uses the 001 `Error` envelope; the client maps `error.code` to `APIError` cases and treats unknown codes as `.unexpected(code)`.

## Deviations from `docs/architecture.md` / ADRs / 001

| Deviation | Justification |
|---|---|
| `POST /v1/auth/logout` exists (§5 lists only `apple` and `refresh`) | Sign-out must revoke the device's refresh token (FR-003); without it a stolen device keeps a 60-day session. One route, no new tables. |
| `GET /v1/me/export` enqueues work (a GET with a side effect) | §5 and the feature decisions name a single `GET /v1/me/export`; the self-enqueuing read keeps the client to one call and is idempotent while an export is pending or fresh (Shared Semantics 10). |
| Faction-change cooldown (30 d) and active-player window (14 d) live in `apps/api/src/modules/factions/rules.ts`, not in `packages/territory-rules` / the doc's "Constants summary" | They are account rules, not territory scoring; adding them to the rules package would require fixtures → TS → Swift → doc for a number the client never uses (it displays server-provided timestamps). A unit test asserts the "Other rules" rows in `docs/territory-rules.md` state the same values, keeping one documented source. |
| Six tabs (Map · Walk · Capture · Collection · Factions · Profile) | Resolves 001's "five tabs" deviation exactly as 001 planned ("Factions arrives with feature 002"); matches §4. |
| Apple-side token revocation on account deletion deferred to 009 | Needs a Sign in with Apple private key, key id and team id the owner has not created (bundle id is still a placeholder). The sign-in request already accepts `authorizationCode` so the client is unchanged later. Recorded in `research.md` R15 and `docs/roadmap.md` is not edited (009 already covers App Store readiness). |
| Rate limiting keeps counters in memory (single API instance) | The stack has no Redis by design (§2); pg-boss/Postgres-backed counters are premature for the beta. Documented in `research.md` R4; a shared store is an operational follow-up. |
| The iOS `APIClient` holds a **copy** of `packages/api-schema/openapi.json` (kept equal by `apps/ios/scripts/sync-openapi.sh` and an equality test in `@nature/api-schema`) instead of a symlink | SwiftPM's generator plugin expects the document inside the target directory; a symlink out of the package root is not guaranteed to be accepted on macOS/Xcode Cloud, and it cannot be verified in the Linux container. |
| `devices` rows are not created at sign-in | Device registration belongs to push (008). `refresh_tokens.device_id` stays null in 002. |
| `Core` Swift package added to §3's list | §4 requires feature packages to depend on core packages; `Core` is that layer and the home of Linux-testable logic (FR-016). |
