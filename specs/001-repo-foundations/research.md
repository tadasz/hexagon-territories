## R1. TypeScript toolchain (pnpm + turbo + tsc + Vitest)

- **Decision**: pnpm 10 workspaces (`apps/*`, `packages/*`) with turborepo 2 for task orchestration; ESM everywhere (`"type": "module"`, `module: NodeNext`); packages built with plain `tsc` into `dist/` (`exports` map with `types`); Vitest 3 as the single test runner; ESLint 9 flat config (`typescript-eslint` type-checked rules) + Prettier 3 at the root. `tsx` for running TypeScript scripts (fixture generator, API dev server).
- **Rationale**: Boring, well-documented, and the `docs/roadmap.md` verification strategy already names Vitest. `tsc` output keeps package consumption trivial (turbo `test` depends on `^build`), avoiding bundler configuration. A single root ESLint/Prettier config prevents per-package drift and root-file collisions between parallel agents (the planner created these root files).
- **Alternatives considered**: tsup/esbuild bundling (unneeded for internal packages); Biome (fewer TypeScript type-aware rules); Jest (slower ESM story).

## R2. H3 in TypeScript and Swift

- **Decision**: `h3-js` 4.x in TypeScript (`latLngToCell`, `cellToParent`, `cellToBoundary`, `polygonToCells`, `gridPathCells`, `cellToChildren`). On iOS, vendor the Uber H3 C core **v4.2.x** into an SPM C target `CH3` (`Sources/CH3/{include/h3api.h, *.c}`) with a Swift wrapper target `H3Kit`. The C target is populated by a checked-in script `apps/ios/Packages/H3Kit/scripts/vendor-h3.sh` that downloads the tagged release, copies `src/h3lib/lib/*.c` and `src/h3lib/include/*.h`, generates `h3api.h` from `h3api.h.in` by substituting the version macros, and writes `Sources/CH3/VERSION` and `LICENSE` (Apache 2.0). The generated files are committed so `swift build` needs no network.
- **Rationale**: No official Swift binding exists; the C core is small (~40 files), Apache 2.0, and identical to what `h3-js` wraps, which is the whole point of fixture parity. Committing the sources keeps Xcode Cloud and Linux CI hermetic.
- **Alternatives considered**: Third-party Swift wrappers (unmaintained, older H3 3.x); binary XCFramework (opaque, not buildable on Linux).

## R3. Fixture format, generator and loading

- **Decision**: Four JSON fixtures under `packages/h3-fixtures/fixtures/`, each with the envelope `{name, description, generator, version, inputs, expected}` (schemas in `data-model.md`). Generated by `packages/h3-fixtures/scripts/generate.ts` using a **seeded PRNG (mulberry32, seed 20260907)** so regeneration is byte-identical; the script is the oracle for `latlng-to-cell` (h3-js) and computes `walk-paths` and `reckoning-weeks` expectations with an intentionally straightforward reference implementation in the script itself (not by importing `@nature/territory-rules`, so a bug in the package cannot leak into the expectations). Hand review is recorded in `packages/h3-fixtures/README.md` (who reviewed which values, e.g. the reckoning table cases). TypeScript loads and validates fixtures with TypeBox schemas (`src/schema.ts`) and `Value.Check`, exporting the JSON Schema files to `schema/*.schema.json`; Swift decodes with `Codable` and a `DecodingError` → `XCTFail("<file>: <path>: <message>")` mapping.
- **Swift fixture location**: tests find the repository root by walking up from `#filePath` until a directory containing `pnpm-workspace.yaml` is found, then read `packages/h3-fixtures/fixtures/<name>.json`. No SPM resource bundling, no symlinks.
- **Rationale**: FR-003 requires a checked-in generator with hand review; TypeBox is already in the stack; `#filePath` lookup works identically on Linux, macOS and Xcode Cloud (source checkout present) and avoids SPM's restriction that resources live inside the target directory.
- **Alternatives considered**: Symlinked resource directory (fragile in SPM), copying fixtures into the Swift package (two sources of truth), ajv (extra dependency).

## R4. `pathToHexMeters` algorithm and PostGIS parity

- **Decision**: Pure geometric splitting by bisection on cell boundaries (see `plan.md` "Shared Rule Semantics" item 7), haversine lengths, DP simplification at 5 m before splitting. The TypeScript package is the authority for metres in `finishWalk` (feature 003); PostGIS `ST_Intersection`/`ST_Length` is used later only as a cross-check and for storage/bbox/MVT, never as the scoring path.
- **Rationale**: One implementation in the rules package can be mirrored in Swift for the client estimate; PostGIS clipping would give a third implementation with its own geodesic model and could not be mirrored on the client. Bisection needs only `latLngToCell`, which both platforms have, and handles segments that cross many cells (spec edge case). Convexity of H3 cells makes "same cell at both ends ⇒ whole segment inside" safe at res 9 (segments are < 200 m after filtering).
- **Alternatives considered**: `gridPathCells` between endpoint cells then exact polygon intersection (needs a polygon-clipping library on both platforms); sampling the segment every 1 m (simple but 10–100× slower and less precise than the ±0.5 m tolerance).

## R5. API skeleton shape

- **Decision**: Fastify 5 with `@fastify/type-provider-typebox`; `@fastify/swagger` in OpenAPI 3.1 mode serving `GET /openapi.json` (no Swagger UI); a `db` plugin holding one `pg.Pool` shared by Drizzle (`drizzle-orm/node-postgres`) and pg-boss; `error-handler` plugin normalising every error to the shared `Error` schema `{error: {code, message, details?}, requestId}`; `jobs` plugin that boots pg-boss 10, registers `reckoning.weekly` with `boss.schedule('reckoning.weekly', RULES.RECKONING_CRON, {}, {tz: 'UTC'})` and a handler that logs `"reckoning.weekly: no work"`. `GET /health` returns 200 `{status:"ok", db:"ok", version}` after `SELECT 1`, or 503 `{status:"degraded", db:"error", version}`. Config via `src/config.ts` (TypeBox-validated `process.env`: `PORT`, `DATABASE_URL`, `LOG_LEVEL`, `S3_*`). Structured logging with Fastify's built-in pino.
- **Rationale**: Exactly the stack in ADR 0002; one pool avoids two connection budgets; a normalised error shape is needed by the generated iOS client from 002 onward.
- **Alternatives considered**: Separate `postgres.js` driver for Drizzle (pg-boss needs `pg` anyway); Swagger UI (not needed, one less dependency).

## R6. Migrations, PostGIS types and partitioning with Drizzle

- **Decision**: Drizzle schema files under `apps/api/src/db/schema/` (one file per §6 group: `enums`, `factions`, `users`, `walks`, `hexes`, `species`, `captures`, `game`, `ops`). PostGIS columns use `customType` (`geography(LineString,4326)`, `geometry(Polygon,4326)`). Migrations live in `apps/api/drizzle/`: `0000_init.sql` generated by `drizzle-kit generate` from the schema, then **hand-edited** to prepend `CREATE EXTENSION IF NOT EXISTS postgis;` and a guarded `DO $$ BEGIN CREATE EXTENSION IF NOT EXISTS h3; EXCEPTION WHEN OTHERS THEN RAISE NOTICE 'h3-pg not available, continuing'; END $$;`, and to replace the plain `location_samples` DDL with `... PARTITION BY RANGE (ts)`; `0001_partitions.sql` (custom) adds a `location_samples_default` partition, a function `ensure_location_samples_partition(month date)` that creates `location_samples_yYYYYmMM` if missing, and calls it for the current and next month. `location_samples` is excluded from Drizzle Kit's diffing (`tablesFilter`) after `0000` so later `generate` runs do not try to "fix" it. Migrations run with `drizzle-orm/node-postgres/migrator` from `src/db/migrate.ts` (`pnpm --filter @nature/api db:migrate`) and automatically in the integration test helper.
- **Rationale**: Drizzle Kit cannot express partitioned tables or `CREATE EXTENSION`; keeping those in reviewed SQL is the documented pattern. The guarded h3 extension keeps the "schema never depends on h3-pg" edge case true.
- **Alternatives considered**: Pure SQL migrations without Drizzle Kit (loses the typed schema ↔ DDL link); `pg_partman` (extra extension for a table we purge at 30 days anyway).

## R7. Database for tests: Testcontainers vs `DATABASE_URL`, and no-Docker mode

- **Decision**: `apps/api/test/helpers/db.ts` resolves the test database in this order: (1) `SKIP_DB_TESTS=1` → every `describe` under `test/integration` is registered with `describe.skip` and prints one line explaining why; (2) `DATABASE_URL` set → use it (this is what `make test` and CI do; the helper creates a throwaway schema/database per run and drops it after); (3) otherwise start `@testcontainers/postgresql` with the image `nature-postgres:16-3.4-h3` if present locally, else `postgis/postgis:16-3.4`. Unit tests under `test/unit` never touch the network.
- **Rationale**: Constitution V wants the real image; agents without Docker still need a green unit suite; CI already has the built image running.
- **Alternatives considered**: pglite (not PostGIS-capable); mocking the DB (violates Constitution V).

## R8. Postgres image with h3-pg, local compose, CI

- **Decision**: `infra/docker/postgres/Dockerfile` `FROM postgis/postgis:16-3.4`, installs build deps + `pgxnclient`, runs `pgxn install h3` (h3-pg 4.1.x), removes build deps, and adds `docker-entrypoint-initdb.d/10-extensions.sql` creating `postgis` and `h3` in the default database. `infra/docker-compose.yml`: `postgres` (build context `infra/docker/postgres`, healthcheck `pg_isready`, volume), `minio` (`minio/minio`, console on 9001, bucket `nature-media` created by a one-shot `minio-init` service using `mc`), `api` (build `apps/api`, `depends_on` healthy postgres, port 3000, `DATABASE_URL=postgres://nature:nature@postgres:5432/nature`). `Makefile`: `dev` (compose up -d postgres minio, run migrations, start API with `pnpm --filter @nature/api dev`), `test` (compose up -d postgres, export `DATABASE_URL`, `pnpm test`), `down`, `db-migrate`, `db-reset`, `lint`. `.github/workflows/api.yml`: on `pull_request` and `push` to `main`; job `rules` (setup-node 22 + pnpm from `packageManager`, `pnpm install --frozen-lockfile`, `pnpm turbo run lint typecheck test --filter=./packages/*`); job `api` (`docker/setup-buildx-action` + `docker/build-push-action` with `cache-from/to: type=gha` to build `nature-postgres:16-3.4-h3`, `docker run -d -p 5432:5432 ...`, wait for `pg_isready`, `pnpm --filter @nature/api test` with `DATABASE_URL`).
- **Rationale**: FR-006/FR-008; h3-pg from PGXN is the `spec.md` assumption; GHA cache makes the compile a one-off. Running the built image in-job satisfies ADR 0009's intent (tests against the real image) without a registry.
- **Alternatives considered**: `services:` container with `postgis/postgis:16-3.4` and no h3-pg (works — h3-pg is optional — but diverges from the local image); publishing to GHCR (deferred until permissions exist).

## R9. iOS project shape and MapLibre in the shell

- **Decision**: `apps/ios/project.yml` (XcodeGen): one app target `NatureExplorer` (iOS 17.0, Swift 6 language mode, `SWIFT_STRICT_CONCURRENCY = complete`), local packages `H3Kit`, `TerritoryRules`, `DesignSystem`, `MapFeature`; MapLibre via SPM `https://github.com/maplibre/maplibre-gl-native-distribution` 6.x, depended on only by `MapFeature`. `RootView` is a `TabView` with five tabs (Map, Walk, Capture, Collection, Profile); non-map tabs are placeholder views from `DesignSystem`. `MapFeature` exposes `MapLibreView: UIViewRepresentable` and `MapConfig` (`styleURL` default `https://tiles.openfreemap.org/styles/liberty`, `initialCenter` Kaunas 54.8985, 23.9036, `initialZoom` 12). `AppContainer` is an `@Observable` class holding protocol-typed services (only `MapConfig` in 001). `ci_scripts/ci_post_clone.sh`: `brew install xcodegen git-lfs`, `git lfs install && git lfs pull`, `xcodegen generate`. App unit tests (`Tests/NatureExplorerTests`) cover `AppContainer` defaults and `resolutionForZoom` via `TerritoryRules`.
- **Linux buildability**: `H3Kit` and `TerritoryRules` have `swift-tools-version: 6.0`, import only `Foundation` (and `CH3`), and pass `swift test` on Linux. `DesignSystem` and `MapFeature` import SwiftUI/MapLibre and are compiled only by Xcode; they are excluded from Linux CI.
- **Rationale**: ADR 0001/0003/0009; OpenFreeMap gives a real basemap at zoom 12 for Kaunas without keys while the Protomaps bucket does not exist yet (deviation listed in `plan.md`).
- **Alternatives considered**: MapLibre demo tiles (no detail at zoom 12); Protomaps hosted API (needs a key); MapLibre SwiftUI DSL (pre-1.0, per ADR 0003).

## R10. Model download and verification, git-lfs

- **Decision**: `ml/scripts/download_models.py` (Python 3.11 stdlib only: `urllib`, `hashlib`, `json`, `argparse`): reads `ml/models/manifest.json`, adds a `files` array per model (`{path, url, sha256, bytes}`), downloads each to `ml/models/cache/<model>/` (gitignored), verifies sha256 against the manifest, and with `--record` writes the computed hash into the manifest when it is `null` (first run) — never overwriting a non-null hash. `--dest DIR` copies verified files to another directory (e.g. `apps/ios/Resources/Models`). `--only NAME` limits to one model; `--skip-download` verifies existing files. Exit codes: 0 ok, 2 hash mismatch, 3 download failure. `ml/tests/test_manifest.py` (unittest) validates the manifest against the schema in `data-model.md` and checks that no `role: primary-on-device` model has a non-commercial licence string. `.gitattributes`: `*.onnx filter=lfs diff=lfs merge=lfs -text` and the same for `*.tflite`; `ml/models/cache/` is ignored by Stream E in `.gitignore`.
- **Model sources**: BirdNET+ V3 preview ONNX and labels from the BirdNET Live app repository's model assets; Geomodel 3.0.4 ONNX from `birdnet-team/geomodel` releases; Perch v2 is manifest-only (Kaggle requires a login; record the URL and leave sha256 `null` with `notes` saying manual download). BirdNET V2.4 is manifest-only (evaluation only, not downloaded in 001). If the container cannot reach GitHub, the task records the blocker in the manifest `notes` and the orchestrator runs the script where network exists.
- **Licence inquiries**: Stream D writes the two email drafts to `ml/licensing/` (Cornell V2.4 commercial terms; Pl@ntNet Pro plan) and adds a "draft ready — to be sent by the owner" status to the inquiry log in `docs/licences.md`; the owner records the sent date. Agents do not send email.
- **Rationale**: FR-009 and Constitution III; stdlib-only keeps `ml/` dependency-free until feature 006 adds the eval harness.
- **Alternatives considered**: `huggingface_hub` / `requests` (extra dependencies for a 100-line script); DVC (heavier than git-lfs for four files).

## R11. ISO week id and time zone handling (deferred)

- **Decision**: `weekIdFor(date, tz)` (`YYYY-Www` in `Europe/Vilnius`) is **not** part of 001. It is implemented with `finishWalk` in feature 003 together with a `week-ids.json` fixture, because the four fixtures named in `spec.md` User Story 1 do not include it and adding a fifth would widen the task (Constitution VI).

## R12. Five tabs, not six

- **Decision**: Tabs in 001 are Map, Walk, Capture, Collection, Profile (`spec.md` FR-007 says five). The Factions tab is added by feature 002 alongside faction selection.
